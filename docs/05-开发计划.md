# InfoPulse 重构开发计划

版本：1.0  
建议节奏：双周迭代。时间为 2-4 人团队估算；单人开发应按容量顺延，不通过压缩测试换取表面进度。

## 1. 交付原则

- 每个阶段必须形成可运行、可验证的纵向闭环。
- 不创建没有真实数据、接口和状态处理的空页面。
- 数据库迁移使用 Alembic，禁止生产环境依赖 `create_all`。
- 所有外部数据源都有契约测试、限流、超时、重试和健康状态。
- 每个 AI 输出都包含引用；没有模型时核心数据浏览仍可用。
- 每次迭代通过后端测试、前端构建、关键流程 E2E 和响应式截图检查。

## 2. 技术前置决策

- 后端：FastAPI、SQLAlchemy Async、PostgreSQL、Redis。
- 后台任务：首期可采用轻量队列；订阅/任务阶段迁移到独立 Worker（Celery、Dramatiq 或 ARQ 三选一后形成 ADR）。
- 搜索：首期 PostgreSQL `tsvector`，数据规模或语言要求超出后再评估 OpenSearch。
- 向量：pgvector；对象存储使用 S3 兼容服务。
- 前端：Vue 3、TypeScript、Pinia、Vue Router；Element Plus 改为按需导入。
- 图表：ECharts；知识/传播网络评估 Cytoscape.js。
- 文档导出：后端生成 Markdown/HTML，Word/PDF 使用独立渲染流程。

## 3. 阶段 0：重构基础（第 1-2 周）

目标：建立不会继续积累技术债的基础。

后端：

- 引入 Alembic，建立开发/测试迁移流程。
- 创建 `data_sources`、`sync_runs`、`content_items`、`events`、`event_contents`。
- 保留现有用户表并编写兼容迁移。
- 建立统一错误、分页、诊断 ID、日志和配置管理。
- 将采集、领域服务和 API 分层。

前端：

- 建立设计令牌和基础组件。
- 重构 AppShell、侧栏、顶部栏、路由分组和权限守卫。
- 建立通用加载、空状态、错误、确认弹窗和引用浮层。
- Element Plus 按需导入，拆分主包。

测试/运维：

- PostgreSQL 集成测试环境。
- CI 执行 Python 测试、类型检查、前端构建和 lint。
- `.env` 校验、密钥检查和健康接口。

验收：全新数据库可从零迁移；现有用户可登录；基础壳在 390/768/1440px 无溢出；旧功能仍可通过兼容路由访问。

## 4. 阶段 1：真实数据中心（第 3-4 周）

目标：稳定采集真实内容并可追溯。

- 实现 Hacker News、GitHub、DEV.to、arXiv、RSS 接入器。
- 实现标准 `ContentItem` 映射、URL 规范化、内容哈希和幂等 Upsert。
- 实现同步运行、超时、重试、游标、限流和部分失败。
- 数据源中心页面：列表、连接测试、立即同步、日志、添加 RSS。
- 数据内容浏览与详情抽屉。
- 对真实端点建立可选择运行的连通性测试；单元测试使用保存的契约样例。

验收：同一来源连续同步两次不会重复入库；每条内容可打开真实原文；来源失败可见且不影响其他来源；Dashboard 不使用硬编码数据。

## 5. 阶段 2：搜索与事件（第 5-6 周）

目标：从内容形成可研究的事件。

- PostgreSQL 全文搜索、筛选、排序、分页和保存搜索。
- 内容类型、语言、来源、时间和互动量标准化。
- 事件自动聚类第一版：标题/正文相似度、实体、时间窗口和来源交叉。
- 事件热度、风险、可信度和状态计算。
- 搜索中心、事件列表、事件详情概览/来源/时间线。
- 人工创建、合并和修正事件，记录审计日志。

验收：搜索结果来自数据库；事件至少包含一个真实来源；聚类可重复执行；人工修正不会被下一次聚类覆盖。

## 6. 阶段 3：Dashboard、Discover 与 Workspace（第 7-8 周）

目标：回答“发生了什么”和“我今天该做什么”。

- Dashboard 聚合指标、趋势、热点和来源健康。
- Discover 系统频道、榜单规则和时间范围。
- 收藏、最近浏览和初版关注主题。
- AI 每日建议规则版：重要度、热度变化、来源质量和用户关注匹配。
- Workspace 聚合今日关注、建议、收藏、浏览和报告入口。
- 推荐反馈和不感兴趣处理。

验收：Workspace 与 Dashboard 数据职责不同；建议能够解释推荐原因；用户反馈影响后续排序；无数据时不生成模拟建议。

## 7. 阶段 4：AI 分析与引用（第 9-10 周）

目标：把现有洞察能力迁移为事件级、可追溯分析。

- `analyses` 和引用表。
- 摘要、观点、争议、原因、影响、风险、预测和建议。
- Prompt 版本、模型配置、结构化输出校验和降级策略。
- 事件详情分析标签页、引用浮层和重新生成。
- 评论来源可用时接入评论分析；无评论时明确禁用。
- 质量评测集：事实引用、格式、无来源断言和中文可读性。

验收：AI 事实结论可以逐条查看引用；模型失败不影响事件原始数据；相同输入保留分析版本；预测明确标识不确定性。

## 8. 阶段 5：AI Agent（第 11-12 周）

目标：提供平台统一自然语言操作入口。

- 会话、消息、引用和反馈模型。
- SSE 流式消息、取消、重试和会话历史。
- 工具：搜索、读取事件、数据聚合、生成分析、创建报告草稿。
- 上下文选择、Token 估算、模型切换和固定事件。
- Agent 页面和全局“询问 AI”入口。
- 工具权限和外部动作确认机制。

验收：用户可从任意事件携带上下文进入对话；回答展示引用；工具调用过程可见；刷新页面可恢复会话；取消不会继续写入完成状态。

## 9. 阶段 6：报告中心（第 13-14 周）

目标：把分析转化为可编辑交付物。

- 报告、版本和导出模型。
- 日报、事件、行业、领导简报和风险报告模板。
- 报告编辑器、目录、引用、AI 改写和版本历史。
- Markdown、HTML 导出；Word/PDF 渲染与视觉验证。
- 从事件、搜索、收藏和 AI Agent 创建报告。

验收：导出文件包含标题、目录、正文、图表和引用；版本可恢复；导出任务失败可重试；报告不引用用户无权访问的资料。

## 10. 阶段 7：订阅、任务与通知（第 15-16 周）

目标：形成持续自动化闭环。

- 订阅、AgentTask、TaskRun、Notification 数据模型。
- 独立 Worker、调度、时区、并发、重试、幂等和死信处理。
- 创建订阅、任务模板、任务编辑器、运行记录和日志。
- 站内通知、邮件和 Webhook；免打扰和通知合并。
- 每日 9 点报告、定时分析企业、关键词变化等模板。
- 费用上限和高风险动作等待确认。

验收：订阅按用户时区执行；重复调度不会重复生成报告；失败产生通知和诊断 ID；任务可暂停、恢复、取消和重试。

## 11. 阶段 8：知识库 RAG（第 17-18 周）

目标：结合公共情报和用户私有知识。

- S3 兼容存储、pgvector 和文档处理 Worker。
- PDF、DOCX、Markdown、TXT 上传及网页导入。
- 安全扫描、解析、分段、向量化、版本和删除。
- 权限过滤、关键词+向量混合检索和重排。
- 知识库 UI、文档预览、检索测试和索引状态。
- AI Agent 选择知识库和公共/私有引用区分。

验收：回答引用到文件页码或段落；用户之间完全隔离；删除文档后不可再召回；解析失败可重试；网页导入通过 SSRF 防护。

## 12. 阶段 9：知识图谱与传播路径（第 19-20 周）

目标：提供高级关联与传播洞察。

- 实体识别、别名归一、关系和事件实体网络。
- 相似事件和关联政策/项目。
- 传播节点、边、证据、置信度和影响力分数。
- 时间轴、网络图和桑基图；提供表格替代视图。
- 传播关系质量评估与人工修正。

验收：每条验证关系有来源证据；推断关系明确标识置信度；无跨平台数据时不生成虚假路径；大型图谱可限制节点数量并保持交互性能。

## 13. 阶段 10：预警与自然语言 BI（第 21-22 周）

目标：完成高级分析和企业工作流。

- 关键词、热度、负面、媒体、官方、传播速度和 AI 风险规则。
- 预警触发、处置、负责人、误报反馈和审计。
- 自然语言到受控分析查询，禁止任意 SQL。
- 动态图表、数据范围解释和查询历史。
- 管理端模型用量、任务健康和审计日志。

验收：预警规则可回放测试；自然语言查询只能访问授权聚合数据；生成图表包含指标定义和数据范围。

## 14. 上线准备（第 23-24 周）

- 性能压测、数据库索引与慢查询治理。
- 安全测试：鉴权越权、SSRF、上传、Webhook、密钥和日志脱敏。
- 数据源条款、隐私政策、保留和删除流程。
- 可观测性：指标、日志、追踪、告警和运行手册。
- 备份恢复演练、Worker 故障和外部 API 降级演练。
- 首次引导、帮助信息和生产配置检查。

上线门槛：P0/P1 缺陷为零；备份可恢复；关键数据源部分失败时系统可用；账户删除和知识库删除验证通过。

## 15. 迭代工作分解模板

每个功能必须包含：

1. 用户故事和验收标准。
2. 数据库迁移和回滚。
3. API、权限和错误码。
4. 前端默认、加载、空、错误、部分失败和权限状态。
5. 单元、集成、契约和 E2E 测试。
6. 日志、指标和诊断信息。
7. 文档和截图验证。

## 16. 测试策略

- 单元测试：领域评分、去重、映射、权限和调度。
- 集成测试：PostgreSQL、Redis、对象存储和 Worker。
- 契约测试：使用真实来源保存样例，检测字段变化。
- 连通性测试：显式启用，在 CI 定时任务运行，不作为每次提交硬依赖。
- E2E：登录、同步、搜索、事件、AI、报告、订阅、知识库。
- AI 评测：引用覆盖率、事实支持率、无来源断言、结构化输出成功率。
- 视觉测试：390、768、1440px；暗色/亮色；长中文和英文标题。

## 17. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 数据源限流/变更 | 官方 API 优先、缓存、游标、健康状态、契约测试 |
| 聚类质量差 | 保留人工合并/拆分、评测集、版本化算法 |
| AI 编造 | 检索约束、逐条引用、无证据拒答、质量评测 |
| 任务重复执行 | 幂等键、分布式锁、唯一运行窗口 |
| RAG 数据泄露 | 查询前权限过滤、租户隔离、审计测试 |
| 成本失控 | 模型分级、缓存、配额、费用上限、任务预估 |
| 功能面过大 | 坚持阶段验收，未形成闭环的模块不提前上线 |

## 18. 阶段完成定义

- 功能通过 PRD 验收标准。
- 数据真实、可追溯，不使用未标识 Mock。
- 数据库迁移可向前执行并有回滚/恢复说明。
- OpenAPI 与实现一致。
- 自动测试通过，关键 E2E 有证据。
- 响应式和无障碍基础检查通过。
- 监控可观察成功、失败、延迟和外部依赖状态。
- 文档更新且不存在已知 P0/P1 缺陷。
