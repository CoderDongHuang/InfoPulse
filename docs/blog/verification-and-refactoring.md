# 从大页面到可验证模块：InfoPulse 的测试分层与渐进重构

更新日期：2026-10-24。[返回主文](./infopulse-open-source-engineering.md) · [专题索引](./README.md)

一个项目可以同时拥有很多模块和很高的修改成本。页面混合 API、路由、输入状态和图编辑时，修复一个交互往往牵动别的功能；后端图校验与数据库、worker 放在同一模块时，单纯检查一个非法节点也可能需要加载整套运行环境。

本轮重构的目标是让职责与验证范围更清楚。它完成第一阶段拆分，没有把所有大页面和复杂业务一次改完。

## 前端按状态所有权拆开

Agent 视图保留模板和真实 DOM 绑定，会话请求、流式生命周期与路由行为进入 composables。编排页进一步分开租户/API 状态与纯本地图编辑：用户添加节点不应依赖一次组织列表加载成功。

| 模块 | 当前职责 | 关键验证 |
| --- | --- | --- |
| [useAgentChat](../../frontend/src/composables/useAgentChat.ts) | 会话请求、流、输入恢复与过期响应隔离 | 迟到流、切换、失败恢复与上下文 |
| [useAgentView](../../frontend/src/composables/useAgentView.ts) | 路由同步、焦点、历史面板、视图生命周期 | 清理旧事件参数、恢复焦点、卸载关闭流 |
| [useOrchestration](../../frontend/src/composables/useOrchestration.ts) | 编排 API 与租户相关状态 | 保留原业务调用边界 |
| [useWorkflowDesigner](../../frontend/src/composables/useWorkflowDesigner.ts) | 本地图的节点、边与表单草稿 | 重复节点、无效端点、删节点时删除关联边 |

拆出 composable 后仍有两个容易遗漏的点。其一，模板 ref 必须绑定回暴露的 ref，测试对象有 `focus()` 不代表页面实际聚焦。其二，本地编辑的宽松检查不能代替服务端图校验，客户端能画出的图不一定可以执行。

下一阶段仍需把模板、列表和表单拆成领域组件，减少高风险 `any` 并收紧 DTO。仅仅把长文件挪到另一个目录，不能解决这些问题。

## 后端先拆没有副作用的规则

[workflow_graph.py](../../backend/app/services/workflow_graph.py)独立处理图校验与下一节点选择，不依赖数据库、worker 或模型。运行时仍可通过原 `orchestration` 路径导入这些函数，避免一次重构迫使所有调用者同步迁移。

校验覆盖节点/边的结构、标识、数量、节点类型、唯一开始与结束、可达性、无环约束、配置和分支歧义。非法结构统一抛出 `ValueError`，避免数组、空配置等输入意外落成类型错误。条件没有匹配且没有默认边时明确失败。

当前不支持并行图，所以同一节点的边不能被任意解释成并行执行。校验器的约束应与运行时能力一致；“接受更多图”并不总是进步。新增[图专项测试](../../backend/tests/test_workflow_graph.py)与既有编排、审计回归一起核对规则和兼容边界。

## 分片前先证明测试没有丢失

后端使用 [test_suites.py](../../backend/scripts/test_suites.py)完整 discovery，再将显式审核的无 fixture 类放入 unit，其余归入 integration。新测试默认不会自动被当作轻量单元测试。

integration 按测试类的稳定哈希分片，保持同一个类及其夹具在同一进程。分片前检查重复、加载失败和过期分类，再验证所有分组的计数与原发现集合完全一致。报告记录计划、实际执行、失败、跳过与耗时；[verify_test_reports.py](../../backend/scripts/verify_test_reports.py)检查跨分片报告的完整性。

这解决的是“提速时有没有漏测”，不等于语句覆盖率或需求覆盖率。即便所有已知测试都执行完，也可能没有覆盖新的失败方式。

## 当前数字必须带提交和范围

2026-10-24、[PR #99](https://github.com/CoderDongHuang/InfoPulse/pull/99)合并版本的记录为：

| 验证 | 记录结果 | 不应推导的结论 |
| --- | --- | --- |
| 前端自动化 | 93/93；类型、生产构建与 bundle budget 通过 | 不是所有界面/输入设备都测试过 |
| 后端专项 | 图、编排、审计 20/20 | 不是本机完整后端回归 |
| unit 分层 | 60/60 | 不是所有数据库与外部链路 |
| 完整 discovery | 324 项，确定性归类 | 发现成功不等于执行成功 |
| API 契约 | 357 条路径 | 路径数量不是能力质量或覆盖率 |
| GitHub CI | 26 项检查通过，含跨平台、容器、浏览器及安全检查 | 不证明实际外部账号、恢复现场与长期 SLO |

本轮本机证据与限制见[开源就绪记录](../audits/2026-10-24-open-source-readiness.md)，测试分层的原始设计见[R15](../audits/2026-10-14-test-layers.md)。历史记录里的 154/188 等数字属于旧版本，不应移植到现在的摘要中。

## 贡献时选择能复现的最小改动

修改逻辑前先描述触发条件与错误结果；随后选择能暴露该问题的验证。例如跨连接持久性就不能只在原 session 读取，DOM 焦点就不能只测试字符串拼接，外部限流就不应在每次 CI 中真实轰击上游。

文档改动需要核对相对链接、截图、命令、版本与能力说明。代码改动按[贡献指南](../../CONTRIBUTING.md)执行相应测试并保留验证范围；真实模型、邮件、对象存储和身份服务需要单独的授权环境，不能用协议 mock 的绿色结果替代。

仓库已有 Issue/PR 模板、CODEOWNERS、路线图与 beta 发布草案。它们能让外部贡献更容易审查；实际稳定性仍取决于持续的小范围修复、可复现证据和后续现场验收。
